# Контекст проекта Carsharing Analytics

Этот файл предназначен для продолжения разработки в новом чате Codex или на другом компьютере. Перед работой также прочитайте `README.md`.

## Цель

Система собирает обезличенные сведения об автомобилях каршеринга и помогает определить:

- какие конкретные автомобили арендуют чаще;
- сколько раз автомобиль исчезал из свободных;
- сколько раз он возвращался в свободные;
- сколько подтверждённых аренд было у автомобиля или модели;
- как долго автомобиль находился в определённом состоянии.

Персональные данные пользователей, телефон, профиль, токены аккаунта и платёжные сведения проекту не нужны.

## Исходное приложение и API

Первичный статический анализ выполнялся по APK приложения `black.voron`. Основной сервер приложения:

```text
https://api.everent.me/
```

Используемые гостевые маршруты:

```text
POST /v9/map.php/free_list_for_guest
POST /v9/map.php/busy_list_for_guest
```

Тело запроса имеет тип `application/x-www-form-urlencoded`:

```text
latitude=55.7558000&longitude=37.6173000
```

Координаты задают область поиска. Автоматический сбор пока не включён.

Другие обнаруженные маршруты, которые сейчас не используются сборщиком:

```text
POST /v9/map.php/list_for_guest
/v9/map.php/*_for_client
/v6/catalog.php/getCatalog/{random}
```

Не добавляйте в репозиторий секреты, токены приложения или сторонних сервисов.

## Подтверждённые поля автомобиля

API может передавать:

```text
id
title
categoryTitle
baseCategoryTitle
typeId
status
stateInfo
stateTime
serviceMode
isAllocated
inGarage
fuel
latitude
longitude
```

`id` — стабильный внешний идентификатор конкретного автомобиля. Статус относится к конкретному автомобилю, а не ко всей модели.

`stateTime` практически подтверждён как количество секунд с начала текущего состояния: при повторных запросах значения разных машин увеличивались на одинаковое число секунд. Сборщик вычисляет `state_started_at = observed_at - stateTime`.

## Статусы

Точные числовые константы из APK:

| Код | Нормализованный статус | Значение |
|---:|---|---|
| 0 | `free` | Свободен |
| 1 | `occupied` | Занят |
| 4 | `unavailable` | Недоступен |
| 12 | `reserved` | Зарезервирован |

У занятой выдачи числовой `status` часто отсутствует. Причина находится в `stateInfo`:

| `stateInfo` | Нормализованный статус |
|---|---|
| начинается с `Оплачено до` | `rented_fixed` |
| `Поминутный тариф` | `rented_minute` |
| `На обслуживании` | `maintenance` |
| `У владельца` | `owner` |
| пустое значение в busy-выдаче | `busy_unknown` |
| новое неизвестное значение | `unknown` |

Технический статус `not_observed` зарезервирован, но его нельзя назначать после единственного отсутствия машины: выдача зависит от области поиска и поведения API.

## Важное правило объединения выдач

`free_list_for_guest` и `busy_list_for_guest` пересекаются. Пересечение не является ошибкой.

Алгоритм:

1. Сначала загрузить free-выдачу.
2. Затем загрузить busy-выдачу.
3. Если ID есть в обеих выдачах, использовать метаданные free при отсутствии полей в busy, но состояние определять по busy и `stateInfo`.
4. Если ID есть только в free, считать автомобиль свободным.
5. Если ID есть только в busy, классифицировать его по `stateInfo`.

В первом снимке было 132 автомобиля в обеих выдачах. Изначально они ошибочно считались конфликтами, затем статусы были восстановлены из сохранённого `stateInfo`.

Первый успешный запуск сборщика:

```text

Уникальных:   287
Free-выдача:  237
Busy-выдача:  182

```

Восстановленное распределение:

| Статус | Количество |
|---|---:|
| `free` | 105 |
| `rented_fixed` | 54 |
| `rented_minute` | 19 |
| `maintenance` | 54 |

Первый снимок является исходной точкой и не создаёт событий аренды.

## Подсчёт событий

Таблица `vehicle_status_history` хранит состояние каждого автомобиля в каждом успешном снимке.

Таблица `vehicle_status_events` получает запись только при изменении статуса уже известного автомобиля.

Основные события:

| Событие | Условие |
|---|---|
| `rental_started` | переход из неарендного состояния в `rented_fixed`, `rented_minute`, `occupied` или `reserved` |
| `returned_free` | переход из любого несвободного состояния в `free` |
| `maintenance_started` | переход в `maintenance` |
| `owner_started` | переход в `owner` |
| `left_free` | переход из `free` в другое состояние, не классифицированный как аренда/обслуживание/владелец |
| `status_changed` | прочее изменение |

Аналитические показатели:

- **подтверждённые аренды** — количество `rental_started`;
- **возвращения** — количество `returned_free`;
- **исчезновения из свободных** — все переходы, где прежний статус `free`, а новый не `free`;
- первое наблюдение не считается переходом;
- при интервале 30 минут короткая аренда, начавшаяся и закончившаяся между снимками, может быть пропущена.

Планируемый интервал автоматического сбора — 30 минут, но планировщик ещё не настроен.

## Структура базы

Каталог:

- `vehicle_types` — виды транспорта;
- `brands` — уникальные марки;
- `vehicle_type_brands` — связь вида и марки;
- `models` — модели марки;
- `vehicle_type_models` — связь вида, марки и модели.

Наблюдения:

- `statuses` — справочник статусов;
- `vehicles` — конкретные автомобили и последнее состояние;
- `collector_runs` — журнал запусков;
- `vehicle_status_history` — снимки состояний;
- `vehicle_status_events` — переходы между статусами.

В `vehicles` пока сохраняется исходный `category_title`. Автоматическое сопоставление каждого автомобиля с `vehicle_type_model_id` ещё не реализовано, потому что `typeId` автомобильной выдачи не совпал напрямую с внешними ID каталога. Не делайте ненадёжное сопоставление только по частичному совпадению строк без проверки.

## Файлы приложения

- `index.php` — каталог транспорта;
- `diagnostic.php` — один ручной запрос без записи в БД;
- `collector.php` — два запроса и атомарная запись снимка;
- `analytics.php` — фильтры, текущие показатели и рейтинги;
- `import_catalog.php` — импорт исходного `catalog.json`;
- `schema.sql` — чистая установка базы;
- `database_dump.sql` — текущая база с данными;
- `migration_*.sql` — история изменений схемы.

Сборщик создаёт запись `collector_runs`, делает два API-запроса и сохраняет автомобили одной транзакцией. Если один API-запрос завершается ошибкой, автомобили и история не записываются, а запуск отмечается как неуспешный.

## Среда разработки

Исходная локальная среда:

```text
Windows
OpenServer
PHP 7.0
MySQL 5.6
URL: http://voron/
Каталог: C:\OSPanel\domains\voron
```

MySQL 5.5 не поддерживает используемое определение нескольких `TIMESTAMP`-полей с `CURRENT_TIMESTAMP`/`ON UPDATE`. Используйте MySQL 5.6 или новее.

Настройки БД по умолчанию:

```text
host: 127.0.0.1
port: 3306
database: voron
user: root
password: пустой
```

Для другой среды используются переменные `VORON_DB_HOST`, `VORON_DB_PORT`, `VORON_DB_NAME`, `VORON_DB_USER`, `VORON_DB_PASS`.

## Развёртывание на другом компьютере

```powershell
git clone https://github.com/EvgenijBaltais/carsharing_app.git
```

Затем:

1. Разместить репозиторий в каталоге сайта OpenServer.
2. Выбрать MySQL 5.6 или новее.
3. Импортировать `database_dump.sql` для переноса текущих данных либо `schema.sql` для чистой базы.
4. Открыть `index.php` через локальный домен.
5. Проверить `analytics.php` и только затем выполнить ручной снимок через `collector.php`.

## Ограничения и осторожность

- Не выполняйте автоматические API-запросы без явного решения владельца проекта.
- Не сохраняйте персональные данные и авторизационные токены.
- Репозиторий публичный. `database_dump.sql` содержит текущие записи автомобилей и координаты, присутствовавшие в API-ответах.
- Не считайте отсутствие автомобиля в одном снимке доказательством аренды.
- Не считайте обслуживание или нахождение у владельца заказом.
- Перед изменением классификации сохраняйте исходный `stateInfo`, чтобы данные можно было переклассифицировать.
